# Unchanged n-body through a numeric interpreter

`input.js` and `LICENSE.md` are byte-for-byte copies from the preserved
`docs/first-projection/benchmarks/nbody/` experiment. The provenance file retains
that experiment's upstream commit and file hashes. There is no handwritten
numeric n-body implementation: the guest's objects, arrays and constructors are
interpreted by the numeric interpreter, then eliminated through specialization.

Run from any directory after building `numeric-project` and `numeric-to-c`:

```
python3 docs/numeric-projection/benchmarks/nbody/run.py
```

`--baseline-only` prepares and measures the direct-C baseline without running the
new projector. The full run uses release binaries. It uses the existing backend executable and runtime read-only;
it does not rebuild that worktree. SHA-256 hashes before and after verify this.

The five paths are original JS, ordinary numeric interpreter, projected numeric
JS, emitted numeric C, and the existing direct C partial evaluator. **Direct C
starts from `input.js`, not the previous experiment's interpreter residual.**
Do not compare its numbers with the old `native-c` experiment as if they were the
same compilation path.

Correctness compares all 64 IEEE-754 bits for inputs 0, 1, 2, 10, 100, 1000, 2500,
10000 and 100000. Performance uses three independent process rounds, each with 5 warmup calls
and 7 samples, at 10000 and 100000. The headline is the median of the three
round medians. JS samples batch enough calls to reach approximately 30 ms, capped at
100 calls. Each child has a 60-second bound (projection has 300 seconds).
Timeouts are recorded rather than substituted with inferred timings.

Process startup and source compilation are excluded. Numeric C includes all
per-invocation numeric buffer allocations and frees. Direct tagged C excludes
context construction/destruction but includes allocations within guest
execution. Both use `clang -std=c11 -O2 -ffp-contract=off` and `-lm`; no fast-math
flags. Executables are temporary and not saved. Sanitizer runs use ASan+UBSan
and `-O1` separately from the timings.

`results.json` contains measured outputs/timings, exact commands, environment,
source hashes, structural checks and sanitizer output. `baseline-results.json`
is only the preliminary direct-path measurement. `residual.js` and `generated.c`
are actual pipeline outputs; `direct-generated.c` is the independent baseline.
The strict numeric emitter validates the allowed subset. The harness additionally
rejects surviving interpreter dispatch/table names, ordinary array/object
initializers and tagged C runtime references.

The interpreter host contract includes `loadF64(a,i) => a[i]` and
`storeF64(a,i,v) => (a[i]=v)`. They preserve read/write ordering during partial
evaluation; the numeric C emitter lowers them to direct indexed operations.
`observe-memory.js` separately instruments allocations and control-buffer
updates. Its overhead is never included in performance measurements.

The residual JS contains a basic-block program-counter trampoline generated by
the partial evaluator. It is not guest AST dispatch. The C emitter recognizes
that restricted form and replaces it with labels and direct branches, removing
the runtime program counter and switch.

## Measured result (2026-11-09, Apple arm64, Node 26.5.0)

Median of three independent seven-sample round medians, milliseconds per call:

| Path | 10,000 steps | 100,000 steps |
| --- | ---: | ---: |
| Original JavaScript | 10.186 | 93.632 |
| Ordinary numeric interpreter | 196.813 | 1955.218 |
| Numeric projected JavaScript | 59.303 | 435.214 |
| Numeric projected C | **1.862** | **18.491** |
| Existing direct tagged C PE | 12.009 | 118.020 |

At 100,000 steps the numeric C is 5.06x faster than original Node, 6.38x
faster than direct tagged C, and 105.74x faster than the ordinary numeric
interpreter. This is one benchmark, not a general JavaScript performance claim.
The projected JS trampoline remains slower than the original guest JS.

All five paths agree bit-for-bit for all nine inputs. ASan and UBSan passed
inputs 0, 1, 100, 10000 and 100000. Three zeroed allocations (4096, 4096 and
4 doubles) total 65,568 payload bytes per call, independent of step count.
Observed heap cursor high-water is 42 doubles; stack cursor high-water is
47 for every positive input (38 at zero steps). This measures the interpreter's
control-buffer cursors, not proof that all possible guest programs fit the buffers.
The generated C has three corresponding allocation calls and three frees, with
direct indexed memory operations and native branches, not tagged values or GC.

## Runtime-n and fairness audit

The step count is not supplied to the partial evaluator. The emitted entry is
`double numeric_main(double input)`; the C timing driver obtains that value from
`strtod(argv[1])`. It is stored in the guest input slot and read by the simulation
loop. There is no baked-in timing step count in generated C. Source and driver
are separate translation units compiled without LTO, and every result is consumed.

`runtime-n-audit.json` records one fresh compilation tested on eight additional,
previously unmeasured values, including 123456 and 10.5. Every output matches the
original bit-for-bit. Execution time also scales about tenfold from 10000 to
100000 steps; the work is not precomputed to a fixed-n result.

Fairness qualifications: the numeric path intentionally assumes a restricted
numeric value/layout contract, whereas the direct tagged backend supports broader
JS semantics. The guest is the existing C-corpus adaptation, not the upstream
scoring harness. JS timing includes result-bit Buffer checking; C formats/checks
its result outside the measured call. A constant-result probe measured about
1.02 microseconds per JS call for that validation overhead, versus about 93.6
milliseconds for the 100000-step original workload. No overhead subtraction was
applied. JS gets five designated warmups plus untimed expectation/pilot calls;
C gets five warmups. Context setup/free is excluded only for the direct tagged
baseline, favoring that baseline rather than the new numeric path.
