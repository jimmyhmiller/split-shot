# Handoff: interpreter specialization and Richards

## Goal

Make Richards faster than ordinary warmed-up Node by specializing an interpreter
with respect to the original Richards JavaScript program, then compiling the
residual program to native code through C.

The interpreter must remain the source of guest-language semantics. Improvements
must apply to general supported programs: no handwritten Richards implementation,
benchmark-specific intrinsics, precomputed answers, or static workload inputs.
Removing AST dispatch is an intermediate milestone; the goal is efficient native
execution of the original object-oriented program.

## Current implementation

The pipeline is:

```text
guest JavaScript + object interpreter
  -> specialize with static guest syntax and dynamic runtime inputs
  -> residual JavaScript using semantic intrinsics
  -> object-to-c
  -> native C plus runtime
```

Specializing the entire interpreter/call graph into one function exhausted a
150-million-expression budget. The working boundary specializes once per static
guest function: Richards produces 42 residual functions including initialization.
Recursive guest calls cross the native call boundary rather than recursively
unfolding during specialization.

Implemented improvements include noncaptured lexical-frame promotion and guarded
known-target native calls. Guards check actual function code identity so prototype
replacement and method shadowing remain correct. Tagged guest values, generic
property operations, and call-frame traffic still remain. Their presence suggests
optimization opportunities; it is not a measured attribution of execution time.

## Recorded performance and correctness

These are saved results, not a new benchmark run for this handoff. The Richards
README identifies semantic implementation commit
`bd1dec2ea2a963c4349c851dae1a61d8bf677f2b` and its complete run on 2026-11-09.

| Path | Runtime COUNT 1000 | Runtime COUNT 10000 |
| --- | ---: | ---: |
| Original Node, module loaded once | 0.0661 ms | 0.6547 ms |
| Ordinary object interpreter in Node | 15.6703 ms | 152.8943 ms |
| Interpreter-specialized native C | 1.1324 ms | 11.3083 ms |

At COUNT 1000, native specialization is approximately 13.84 times faster than the
ordinary interpreter but **17.13 times slower than the target Node baseline**.
The objective has not been achieved. A separate paired native-stage experiment
shows approximately 1.75 times improvement from frame promotion and guarded calls.

The saved full run reports 90 cross-path correctness comparisons, 15 native
ASan/UBSan cases, and 42 intended invalid-input errors. These are finite checks,
not full JavaScript conformance. The runtime retains guest allocations until
entry completion and releases them then; it has no tracing collector. Captured
lexical environments also have explicit bounded capacity.

## Prior work to study

### Similix: a concrete Scheme interpreter specialization example

[Generating Action Compilers by Partial Evaluation — Anders Bondorf and Jens
Palsberg, FPCA 1993 / JFP 1996](https://www.cs.ucla.edu/~palsberg/paper/jfp96.pdf)
specializes a Scheme action interpreter using Similix. **Read section 5 and
Appendix B**, which publish the binding-time improvements and interpreter source.
The generated language is Scheme rather than C. Static control information,
partially static data, and deliberate limits on unfolding matter to the result.

This is the closest historical source for understanding how interpreter structure
affects specialization quality. Compare its techniques with our small-interpreter
experiments rather than assuming a direct translation will work.

[Similix source mirror](https://github.com/shih-liang/Similix) includes examples and
the manual. The author-maintained [Jones, Gomard, and Sestoft book resource
page](https://studwww.itu.dk/people/sestoft/pebook/) provides the full book,
example specializers, and Similix/C-Mix distributions. No external implementation
was built or benchmarked during this research.

### Lancet: analysis beyond eliminating dispatch

[Surgical Precision JIT Compilers — Rompf et al., PLDI
2014](https://www.cs.purdue.edu/homes/rompf/papers/rompf-pldi14.pdf), particularly
sections 2.1–2.2, derives a compiler from a JVM bytecode interpreter through LMS
staging. Its frame uses `Array[Rep[Object]]`: the structure is available during
compilation while elements denote runtime values. It adds an abstract store and
fixed-point analysis to optimize residual operations, including object accesses.
[Source code](https://github.com/TiarkRompf/lancet).

Inference for our project: known environment/layout structure should survive even
when stored values are dynamic. Optimizing opaque object intrinsics requires
sound representation and effect information. Explicit LMS staging differs from
our automatic JavaScript partial evaluator; this is an architectural reference.

### Truffle: dynamic object specialization

[Official Truffle partial-evaluation documentation](https://www.graalvm.org/dev/graalvm-as-a-platform/language-implementation-framework/PartialEvaluation/)
explains stable metadata, inlining boundaries, frame scalar replacement, and
guarded specialization. A stable layout field on a dynamic receiver does not
automatically become a compilation constant. Speculation relies on invalidation
and deoptimization machinery.

For our AOT pipeline, layout/type facts must be proven or guarded with a correct
fallback. A JIT assumption cannot be copied without its recovery mechanism.

### Scheme-to-C is related, but does not identify the technique

Generating C does not imply compilation by specializing an interpreter.
[Cyclone's compiler account](https://justinethier.github.io/cyclone/docs/Writing-the-Cyclone-Scheme-Compiler-Revised-2017)
describes closure conversion and explicit C generation. Stalin's
[Flow-Directed Lightweight Closure Conversion — Jeffrey Mark
Siskind](https://engineering.purdue.edu/~qobi/papers/fdlcc.pdf) describes whole-program
analyses useful for efficient closures and storage. Those analyses are relevant
to representation costs, but are distinct from Similix-style specialization.

### AOT specialization of existing systems-language interpreters

[Partial Evaluation, Whole-Program Compilation — Fallin and
Bernstein](https://arxiv.org/abs/2411.10559) specializes C/C++ interpreters at
SSA/basic-block level, with applications to SpiderMonkey and Lua. It is another
direct reference for interpreter-derived compilation. Its speedups over
interpreters do not establish superiority to Node for our workload.

## Recommended next work

1. Read the Similix interpreter and binding-time improvements alongside our saved
   small-interpreter results. Preserve negative results; do not repeat changes
   based only on AST encoding or residual source size.
2. Construct a minimal executable object interpreter example with a fixed layout,
   mutable numeric field, method call, and dynamic input. Compare visible semantic
   operations with the current intrinsic boundary, keeping guest behavior fixed.
3. Inspect lookup, tagging, frame storage, allocation, and call plumbing
   separately in residual JS, generated C, and optimized native code. Maintain
   correct aliasing, mutation, receiver, and evaluation-order behavior.
4. Use Lancet's staged-frame/abstract-store distinction to identify missing facts.
   Implement general PE analysis or intrinsic effect/representation information
   where evidence justifies it. Avoid spreading evaluator-specific identity-write
   staging aids instead of addressing their underlying limitation.
5. Carry validated techniques into the object interpreter. Likely areas include
   typed fields, unboxed values, and native function signatures, but these remain
   hypotheses until residual inspection and measurement establish their benefit.
6. Re-run semantic checks and fair Richards measurements. Continue until the
   interpreter-specialized native path beats ordinary warmed-up Node, or clearly
   document the remaining obstacle without claiming the objective is complete.


Consult the benchmark README before running: it documents baseline availability
and options including `--skip-direct`. Keep exact repeat-count and runtime-COUNT
adapters distinct. Workload inputs remain dynamic during specialization. Preserve
original-source oracles, result consumption, warmup, independent process rounds,
raw samples, source hashes, and native allocation/cleanup inside each timed call.
Compilation remains outside runtime timing, with compilation failures and costs
reported separately. Fresh-module Node is an additional comparison; beating it
does not meet the goal of beating ordinary module-once Node. Do not mix medians
from separate runs or substitute a handwritten direct-C compiler for this route.
